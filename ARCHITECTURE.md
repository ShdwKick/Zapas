# «Что у нас есть?» — план архитектуры

`client_id` и каталог — `zapas`, домен `zapas.burninghouse.ru`. Название
рабочее, может поменяться (в коде — константа `SERVICE_NAME` в `server.js` и
`assets/app.js`, плюс `index.html`). Вещество — магний: `--flame-tip #e8f0ff`,
почему не барий — в «Оформлении».

Что это: учёт того, что лежит дома и у чего есть срок. Первый и пока
единственный раздел — **аптечка**: что есть, когда истекает, где лежит,
сколько осталось. Дальше — гигиена, бытовая химия, сменные фильтры; ядро
с первого дня общее, чтобы второй раздел не потребовал переделки схемы.

Главная механика: **поднёс упаковку к камере — она добавилась**. Всё
остальное построено вокруг того, чтобы учёт не превратился в ввод данных.

---

## Граница: сервис ведёт учёт, а не лечит

Это решение, а не оговорка, и оно раньше всех остальных.

Сервис **не показывает** показания, дозировки, способ применения,
противопоказания и совместимость. Не отвечает на «что выпить от головы».
Не советует замену, когда срок истёк. На карточке препарата есть ссылка на
официальную инструкцию — и на этом участие сервиса в лечении заканчивается.

Причина простая: всё, что сервис скажет о применении, человек прочитает как
рекомендацию, а проверить её будет нечем. Ошибка здесь стоит здоровья, а
польза мизерная — бумажка и так лежит в коробке. Поэтому поля вроде
«показания» в схеме нет вовсе: нет поля — нечего однажды вывести на экран
«просто чтобы было удобнее».

Что сервис про препарат всё-таки знает — срок, условия хранения, МНН, форма,
рецептурность — перечислено ниже и обосновано отдельно: это свойства
**упаковки**, а не терапии.

## Стек

Как у PDD и Brain: один `server.js` на `node:http` + `node:sqlite`, без
`node_modules`, статика в `assets/`, `auth-client.js` скопирован из Auth.
Роутинг через History API (`/aptechka`, `/mesto/vannaya`, `/item/…`), сервер
отдаёт на все валидные пути один `index.html`. Docker + Watchtower, nginx на
443, как у всех.

Порт dev: **8799** (8795 — brain, 8796 — занят e2e, 8797 — movieporter-site,
8798 — pdd).

Данные — `data/zapas.db` (в контейнере volume). Справочники (`bank/`) — часть
образа, как билеты у PDD: в рантайме сеть не нужна.

PWA обязательна — сервисом пользуются стоя у шкафчика в ванной, с телефона и
часто без нормальной связи: `manifest.webmanifest`, `sw.js`, очередь
отправки, как `progress.js` у PDD.

## Модель данных

Разделение «что это» и «что у нас лежит» — то, без чего такой сервис
ломается на второй неделе: дома три упаковки ибупрофена с разными сроками, а
препарат один.

```sql
-- ЧТО это. Каталог дома, одна строка на препарат/средство.
CREATE TABLE items (
  id              TEXT PRIMARY KEY,
  household_id    TEXT NOT NULL,
  kind            TEXT NOT NULL,     -- 'drug' | 'hygiene' | 'household' | ...
  gtin            TEXT,              -- из кода упаковки; NULL у добавленных руками
  name            TEXT NOT NULL,
  mnn             TEXT,              -- действующее вещество (из инструкции)
  form            TEXT,              -- 'капли для приема внутрь'
  dose            TEXT,              -- '200 мг'
  pack_qty        REAL,              -- сколько единиц в целой упаковке
  unit            TEXT,              -- 'таб' | 'мл' | 'шт'
  after_open_days INTEGER,           -- годен N дней после вскрытия
  storage_max_c   INTEGER,           -- верхняя граница температуры хранения
  rx              INTEGER,           -- 1 — по рецепту
  leaflet_url     TEXT,              -- ссылка на официальную инструкцию
  source          TEXT NOT NULL,     -- 'manual' | 'leaflet' | 'off'
  created_at      INTEGER NOT NULL
);

-- ЧТО у нас лежит. Одна строка — одна физическая упаковка.
CREATE TABLE packs (
  id         TEXT PRIMARY KEY,
  item_id    TEXT NOT NULL,
  place_id   TEXT,
  expires_on TEXT,                   -- 'YYYY-MM', см. ниже
  opened_on  TEXT,                   -- 'YYYY-MM-DD' или NULL
  qty        REAL NOT NULL,          -- сколько осталось, в units позиции
  serial     TEXT,                   -- (21) из DataMatrix — дедуп упаковки
  status     TEXT NOT NULL,          -- 'have' | 'used' | 'discarded'
  added_by   TEXT NOT NULL,
  added_at   INTEGER NOT NULL
);
CREATE UNIQUE INDEX packs_serial ON packs(serial) WHERE serial IS NOT NULL;

-- ГДЕ лежит. Дерево: «Дом → ванная → верхний шкафчик», «Дача», «Рюкзак».
CREATE TABLE places (
  id           TEXT PRIMARY KEY,
  household_id TEXT NOT NULL,
  parent_id    TEXT,
  name         TEXT NOT NULL,
  sort         INTEGER NOT NULL DEFAULT 0
);

-- ЖУРНАЛ. Нужен для отмены, истории «что закончилось» и списка докупить.
CREATE TABLE events (
  id      TEXT PRIMARY KEY,
  pack_id TEXT NOT NULL,
  user_id TEXT NOT NULL,
  kind    TEXT NOT NULL,             -- 'add'|'take'|'open'|'discard'|'move'|'undo'
  qty     REAL,
  at      INTEGER NOT NULL,
  note    TEXT
);
```

Решения, которые тут зашиты:

- **`kind` с первого дня.** Ровно как `habit='pdd'` у стрика: вторая тема
  добавляется строкой, а не миграцией. Но экраны и поля первой версии —
  только про аптечку, иначе интерфейс расползётся до «универсального
  инвентаря», которым никто не пользуется.
- **Каталог принадлежит дому, а не миру.** Соблазн сделать общий на всех
  каталог GTIN большой, но тогда одна опечатка видна всем домам, и появляется
  модерация — работа, которой у домашнего сервиса не должно быть. Дома
  обмениваются только через импорт `bank/` (см. «Инструкции»).
- **Остаток — дробный (`REAL`).** Половина таблетки и «примерно треть
  флакона» — нормальная жизнь аптечки. Целые числа заставят врать.
- **Журнал, а не только текущее состояние.** «Выбросил по ошибке» случается
  чаще, чем кажется, а список докупить честно строится только из истории.

## Срок годности

**Храним месяц, не день.** На упаковках печатают `MM.YYYY`, и выдуманный день
создаёт ложную точность. `expires_on` — `'YYYY-MM'`, препарат считается годным
**до конца месяца**. Ввод — два барабана, месяц и год, а не календарь: календарь
на телефоне требует трёх тапов и промахивается.

**Фактический срок** — минимум из двух:

```
effective = min(конец месяца expires_on,
                opened_on + after_open_days)
```

Это главный выигрыш сервиса над списком в заметках. Капли, сиропы и мази
после вскрытия живут недели, а на упаковке по-прежнему стоит 2028 год, и
никто этого не помнит. `after_open_days` приезжает из инструкции (см. ниже)
или вводится один раз руками на позицию.

Состояния и подсветка:

| Состояние | Когда | Как показано |
|---|---|---|
| годно | больше 90 дней | обычная карточка |
| скоро | 90…31 день | жёлтая метка со сроком |
| вот-вот | 30…1 день | оранжевая, поднимается наверх списка |
| истекло | срок прошёл | красная, отдельная группа сверху |
| вскрыто | есть `opened_on` | показан фактический срок, а не печатный |

Счёт дней — по часовому поясу пользователя (`profiles.tz`), как у PDD: иначе
у человека во Владивостоке срок истекает в обед.

## Сканирование

Что реально есть на упаковке российского лекарства — **DataMatrix МДЛП**:

```
01 <GTIN-14> 21 <серийный номер> 91 <…> 92 <…>
```

Ни названия, ни срока годности в коде нет — срок печатают текстом рядом.
Поэтому ожидание «поднёс — приехали все данные» выполнимо только наполовину,
и это заложено в поток добавления, а не обнаружено потом.

**Как читаем.** Два движка за одним интерфейсом (`assets/scan.js`):

- Chrome на Android — нативный `BarcodeDetector`, DataMatrix через ML Kit.
  Берём его, **только если он умеет `data_matrix`**: детектор без этого
  формата бесполезен там, где лежат лекарства.
- Safari на iOS — API нет (выключено по умолчанию вплоть до 26/27), работает
  вендорный `zxing-wasm` в `assets/vendor/zxing/`. Копия вместо зависимости —
  тот же приём, что с `brand.css` и `auth-client.js`.
- Desktop Chrome на Linux/Windows — API нет, тот же wasm.

Цена копии — **925 КБ бинарника в репозитории** (около 400 КБ по сети, он
хорошо жмётся). Грузится лениво, при первом открытии сканера, и только там,
где нет нативного детектора: на Android эти килобайты не скачиваются вовсе.
В `SHELL` service worker'а он намеренно не входит — попадает в кэш сам после
первого использования. Подробности и проверка целостности —
`assets/vendor/zxing/VENDOR.md`.

Одна кодовая база, нативной обёртки на старте не нужно. Android-приложение
(как у PDD) имеет смысл потом и ради виджета «что истекает», а не ради камеры.

**Поток добавления** — три шага, из которых обычно нужен один:

1. Камера находит код → парсим GS1: `01` → GTIN, `21` → серийник,
   `17` → срок, **если он есть** (на лекарствах РФ обычно нет, на импорте и
   непрепаратах бывает — тогда подставляем и не спрашиваем).
2. **GTIN знаком** (есть в каталоге дома или в `bank/`) → карточка заполнена,
   спрашиваем только срок и количество. Два тапа, и это 95% случаев: дома
   покупают одно и то же.
3. **GTIN незнаком** → спрашиваем название один раз, с автокомплитом по
   `bank/`. Связка `gtin → item` сохраняется навсегда; следующая такая
   упаковка пойдёт по шагу 2.

**Дедуп по серийнику.** `21` уникален для физической упаковки, поэтому
повторный скан той же коробки не создаёт вторую запись, а открывает
существующую («эта упаковка уже в ванной, осталось 12 таблеток»). Ни один
ручной трекер так не умеет, а ошибка «добавил дважды» — самая частая.

**Уникальность серийного — внутри дома, а не на весь сервис.** Поэтому
`household_id` продублирован в самих `packs` и `events`, хотя его видно и
через `items`: глобальный уникальный индекс означал бы, что добавление
коробки в одном доме падает из-за чужого дома, а дедуп возвращает человеку
чужую упаковку. То же касается `rid` из офлайн-очереди — его придумывает
клиент, и уникальным он может быть только внутри дома.

**Чего ждать от настоящих сканеров.** Две вещи, на которых легко обжечься и
которые поэтому разобраны в `assets/gs1.js` явно:

- Разделитель `\x1d` теряется или приезжает печатным текстом `<GS>`/`{GS}` —
  нормализуем оба вида. Это не теория: проверено на коде, нарисованном
  писалкой того же zxing, — она пишет именно печатный вариант.
- Разделителя нет вовсе, и за серийным сразу идёт крипто-хвост. В МДЛП
  серийный ровно 13 знаков — этим и режем, когда дальше видим `91`/`92`/`93`.
  Без этого серийник съедал бы весь хвост, и дедуп ломался бы молча.

Серийник больше ни для чего не используем: проверка оборота через МДЛП —
не наша задача, а хранить его дольше, чем живёт упаковка, незачем. Вместе с
`packs` он и уезжает.

## Инструкции: извлечение полей, а не пересказ

Официальная бумага — инструкция по медицинскому применению. Из неё берутся
`after_open_days`, `storage_max_c`, `mnn`, `form`, `rx`. Делает это GigaChat
(ключ `GIGACHAT_AUTH_KEY`, как у Trip), но **как извлекатель фактов, а не
автор краткой версии**.

Разница принципиальная. Пересказ — текст, в котором ошибка неотличима от
правды: читатель не видит, что потерялась оговорка. Извлечение проверяемо:
поле, значение и дословная цитата, которую можно найти в документе.

**Каждое поле приезжает с цитатой, и цитата сверяется автоматически.**
Инструмент берёт текст PDF, нормализует пробелы и переносы и проверяет, что
цитата в документе действительно есть. Не нашлась — поле не попадает в банк,
а уходит в ручной просмотр. Так галлюцинация становится технически
невозможной, а не маловероятной.

### Что проверено на живом примере

Прогнал официальную инструкцию Минздрава РФ (Синупрет, капли, П N014247/01,
4 страницы) через `GigaChat-2-Max` вложением (`POST /api/v1/files`,
`purpose=general`, затем `attachments` в сообщении):

- модель вернула JSON по заданной схеме; **5 цитат из 5 нашлись в документе
  дословно**;
- `after_open_days: 180` — «После вскрытия флакона: не более 6 месяцев»,
  `storage_max_c: 25`, `rx: 0`, номер РУ и форма совпали с титульным листом;
- одна ошибка — и в безопасную сторону: модель сказала, что держателя РУ в
  документе нет, хотя он есть на третьей странице. Пропуск, не выдумка;
- **1771 токен промпта + 149 ответа** на препарат. Пятьсот позиций — около
  миллиона токенов, бесплатного лимита хватает с запасом.

Две грабли, которые эта проверка вскрыла:

- **Переносы.** В PDF встречается «при темпе - ратуре»: модель склеивает
  правильно, наивная сверка `цитата in текст` — спотыкается. Нормализация
  переносов обязательна, иначе верификатор врёт на каждой второй строке.
- **Интернет противоречит бумаге.** Украинский справочник для того же
  препарата пишет «3 месяца после вскрытия», в российской инструкции — 6.
  Разные регистрации. Сверяться можно только с документом, и в карточке
  должно быть видно, из какого именно документа поле взято.

### Фотография вкладыша

Собрать инструкции заранее нельзя: препаратов слишком много, и предугадать,
что лежит у людей, невозможно. Зато коробка у человека в руках ровно тогда,
когда он заводит упаковку. Поэтому вкладыш можно сфотографировать, и поля
заполнятся из него.

Правила те же, что у офлайн-инструмента, плюс два, которые найдены
экспериментом на настоящей странице инструкции (обычный снимок и
намеренно плохой — 560 пикселей с сильным сжатием):

- **Пересчёт единиц делает код, а не модель.** На плохом снимке GigaChat
  прочитал «не более 6 месяцев» верно, а в поле «дней» положил `6`. Цитата
  при этом настоящая, то есть сверка цитат такую ошибку **не ловит в
  принципе**. Теперь у модели спрашивают только напечатанное — число и
  единицу отдельно, — а арифметика в `assets/expiry.js`. После правки оба
  снимка дали одно и то же: 180 дней.
- **Название со снимка не применяется.** Модель дважды прочитала «Синупрет»
  как другой реальный препарат — «Синуфорте» и «Сипнур». Название и так
  известно: его ввёл человек или оно пришло с кода упаковки. Со снимка оно
  берётся только для предупреждения «кажется, снята не та коробка».

Что проверка цитат **не** доказывает для фотографии: текстом документа здесь
служит то, что распознала сама модель, поэтому сверка ловит выдуманные
факты, но не ловит неверно прочитанную цифру. Отсюда обязательный экран
подтверждения, где рядом с каждым полем показана цитата, а в подписи прямо
сказано, что сверить надо с бумагой в руке.

Остальное: снимок нигде не сохраняется (только отправляется и забывается),
лимит `PHOTOS_PER_DAY` на человека — промах по кнопке в цикле не должен
выедать лимит токенов, и `GIGACHAT_AUTH_KEY` нужен только для этого; без
него сервис работает целиком, просто не предлагает фотографировать.

### Общий каталог

То, что подтвердил один дом, достаётся остальным — иначе каждая семья
заполняла бы одни и те же препараты заново. Это и делает справочник
самозаполняющимся: первый владелец препарата тратит десять секунд, дальше
он бесплатен для всех.

- **Вклад анонимен.** В таблице `catalog` нет ни `user_id`, ни
  `household_id`: по каталогу не должно читаться, кто чем лечится. Есть
  тест, который проверяет отсутствие таких колонок.
- **Доверие по источнику:** инструкция (`leaflet`) > снимок (`photo`) >
  слова (`user`). Источник не хуже прежнего перекрывает значения, хуже —
  только дозаполняет пустые.
- **Совпавшие значения — подтверждение.** Второй дом с тем же числом
  увеличивает счётчик, расхождение — нет; в карточке видно и источник, и
  сколько раз подтверждали.
- **Аптечки при этом не общие.** Каталог знает про препараты, а не про то,
  у кого что лежит.
- Рядом таблица `wanted`: чего каталогу не хватает. Она наполняется по
  реальному употреблению, и по ней видно, какие инструкции имеет смысл
  разобрать офлайн-инструментом.

### Откуда берутся сами инструкции

**ГРЛС закрыт капчей.** Поиск требует не только POST с `__VIEWSTATE`: в
параметрах запроса сидит `token`, выдаваемый после ввода кода с картинки.
Автоматического импорта «все инструкции из ГРЛС» не будет — и обходить капчу
мы не станем. Тот же документ часто открыто лежит на сайте производителя, и
это законный способ его получить.

Отсюда схема с человеком в цикле, но с человеческой работой «скачать файл»:

1. PDF кладётся в папку (из ГРЛС руками или с сайта производителя).
2. `tools/leaflet.mjs` прогоняет папку: извлекает текст (`tools/pdftext.mjs`,
   свой разбор `ToUnicode` без зависимостей), спрашивает GigaChat, сверяет
   каждую цитату с текстом и пишет `bank/leaflets.json` (ключ — номер РУ).
3. Поля без подтверждённой цитаты в банк не идут — инструмент называет их в
   отчёте, чтобы было видно, что именно он отбросил и почему.
4. Банк — часть образа. **В рантайме ни сети, ни ключа GigaChat.**
5. Сервис подставляет `afterOpenDays`, `storageMaxC`, `rx` и форму, когда
   человек заводит позицию с точно таким же названием. Совпадение строгое:
   «Нурофен» и «Нурофен Форте» — разные препараты. Введённое руками всегда
   важнее справочника: человек смотрит на свою упаковку.

Незнакомые позиции сервис складывает в таблицу `wanted` (РУ/GTIN + сколько
домов спрашивало), список виден в Admin — пачка на следующий прогон. Ровно
как `tips-own.json` у PDD: батчами, с проверкой.

Сканы из ГРЛС отсеиваются сами: в них нет текстового слоя, сверять цитату не
с чем — поля остаются пустыми. **Пустое поле честнее придуманного.**

Технические мелочи, на которых иначе теряется вечер:

- Сертификат GigaChat подписан корнем Минцифры, которого нет в системных
  хранилищах. Нужен явный корневой сертификат: `NODE_EXTRA_CA_CERTS` или
  `ca` в `https.Agent`. Системный `curl` на macOS собран на SecureTransport и
  `--cacert` не понимает вовсе — проверять надо не им.
- `temperature` около нуля и строгая схема в промпте; хеш PDF сохраняем,
  чтобы не спрашивать повторно о том же документе.
- Извлечение текста из PDF — свой разбор `ToUnicode` CMap и операторов
  `Tj`/`TJ`, ~60 строк, без зависимостей. Прототип на Python написан и
  проверен, для `tools/` переписывается на JS.

## Дом

Аптечка по смыслу общая, поэтому данные принадлежат **дому**, а не человеку.
Одиночка — дом из одного, никакой разницы в интерфейсе.

```sql
households         (id, name, created_by, created_at)
household_members  (household_id, user_id, role, joined_at,
                    PRIMARY KEY (household_id, user_id))
```

Участники приглашаются **из списка друзей Auth** (`GET {AUTH_ISSUER}/api/friends`
с Bearer пользователя, как у Brain и PDD) — своего списка контактов не
заводим: кто кому друг, решает Auth. Сервер проверяет дружбу перед тем, как
создать приглашение: поиска людей в сервисе нет и быть не должно, иначе по
чужому `user_id` можно звать кого угодно.

Правила, которые стоило решить один раз:

- **Последний участник выйти не может.** Дом с данными остался бы ничьим, а
  «выйти» молча стёрло бы общую аптечку. Хочешь стереть — есть «удалить мои
  данные», там это названо своим именем.
- **Ушёл владелец — дом переходит** к тому, кто здесь дольше всех. Иначе
  некому приглашать и убирать участников.
- **Убрать другого может только владелец**, и не себя.
- Данные остаются дому, а не уезжают с человеком: иначе уход одного
  опустошает общую аптечку.

Человек может состоять в нескольких домах (своя квартира и дача родителей),
активный переключается в шапке.

Показывая, кто добавил упаковку, берём `user.name || user.username`.

## Напоминания

Два канала, оба уже есть в доме: web push (свой `lib/webpush.js`,
копируется из PDD) и уведомления Auth.

| Событие | Когда | Кому |
|---|---|---|
| `expiring` | за 30 дней до конца срока | каждому в доме, раз на упаковку |
| `expired` | срок прошёл | каждому в доме |
| `openExpiring` | за 3 дня до конца срока после вскрытия | каждому в доме |
| `low` | остаток ниже порога позиции | каждому в доме |
| `zapas.invite` | позвали в дом | приглашённому |
| `zapas.invite_accepted` | приглашение приняли | пригласившему |

Первые четыре — поводы внутри одной дневной сводки, их можно выключать
по отдельности; последние два — события, они приходят сразу.

Планировщик — раз в 5 минут, как у PDD. «Пора» — это **местное время
перевалило за выбранное И сегодня ещё не рассылали**, а не попадание в
пятиминутное окно: перезапуск контейнера в это окно не должен съедать
напоминание за день. По умолчанию 10:00 по местному.

**Одно сообщение в день, пачкой** («2 упаковки истекли, 1 заканчивается»), а
не уведомление на каждую упаковку: иначе после первой же ревизии аптечки
человек выключит push и больше не включит.

Повторы гасит таблица `notified` (человек + упаковка + повод): про одну и ту
же коробку «истекает» приходит один раз, а не каждый день до конца срока.
Отметка одного участника не гасит напоминание другому — у каждого своё время,
свои поводы и свой счёт.

VAPID-ключи генерируются сами при первом запуске и лежат в `data/vapid.json`.
Сменить их — значит обнулить все подписки браузеров.

## Гость и офлайн

Как у Brain и PDD: **без входа работает всё** — добавление, сроки,
подсветка, сканер. Прогресс в `localStorage`. Вход добавляет три вещи: общий
дом, напоминания и синхронизацию между устройствами. При первом входе
гостевая аптечка переносится на сервер (позиции и упаковки — как есть).

Офлайн — очередь (`outbox`) с `rid` у каждой операции: сервер не засчитает
повтор, если запрос дошёл, а ответ потерялся. Отправка при запуске, по
событию `online`, при возврате во вкладку и раз в 30 секунд, пока очередь не
пуста. На экране всё применяется сразу, под карточкой — «отправится само».

`sw.js` кеширует оболочку и справочник: у шкафчика в ванной связь ловит плохо.

## Оформление

**Вещество — магний**, пламя яркое бело-голубое над красным углём.

```css
:root{
  --flame-base:#7f1d1d; --flame-tip:#e8f0ff;
  --night-1:#0b0d12;    --night-2:#171d2b;
  --dawn-1:#f7f9ff;     --dawn-2:#dde6f7;
}
```

**Почему не барий**, который числится свободным в реестре: бледно-зелёная
вершина (`#a7f3a0`) в панели вкладок на 16 пикселях путается с бором у
«Что собираем?» (`#7ddf3c`). Правило из `Design/services.md` на этот случай
прямое — берём другое вещество, а не подкручиваем оттенок. Магний белый,
ни с чем в ряду не спорит, и для шкафчика с лекарствами читается
«чисто», а не «аптечно-зелёно». Строку в реестр веществ надо дописать.

**Сводка — она же фильтр.** Четыре блока наверху («истекло», «вот-вот»,
«скоро», «всего») не просто считают: клик по блоку оставляет в списке только
эти упаковки, повторный клик снимает фильтр, «всего» сбрасывает. Сами цифры
под фильтром **не меняются** — они всегда про всю аптечку, иначе фильтр съедал
бы ту самую сводку, ради которой на неё смотрят. Пустая группа не нажимается:
счётчик остаётся на месте, но вести в пустой список незачем.

**Повадка искр:** искры гаснут по одной, сверху вниз — то, что лежит дольше,
гаснет первым. На телефоне искр вдвое меньше, при `prefers-reduced-motion`
они замирают на половине высоты и не гаснут.

Остальное — общее: знак inline, локап по `Design/mark.md`, фавикон отдельным
файлом с вписанными цветами из `Shared/mark-small.svg`, компоненты на токенах
Material 3, пламя только в трёх местах.

Отдельно про подсветку сроков: красный и жёлтый здесь — **сигнал**, как
лампы на приборке у PDD, и они не конкурируют с пламенем, потому что пламя
бело-голубое. Это и был второй довод за магний.

## Подключение

1. `docker compose exec auth node server.js client-add zapas "Что у нас есть?" https://zapas.burninghouse.ru/`
2. Скопировать `auth-client.js` и `auth-client-browser.js` из `Auth/client/`.
3. Дописать строку в `TARGETS` в `Shared/sync.mjs` (`Zapas/assets` и
   `Zapas` для `admin-internal.js` + `set-env.sh`), прогнать `node Shared/sync.mjs`.
4. Поставить хук: `cp ../Shared/pre-commit .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit`
5. Вписать сервис в `Design/services.md` и `Design/palette.md`.

Окружение: `AUTH_ISSUER`, `AUTH_CLIENT_ID=zapas`, `ADMIN_INTERNAL_KEY`,
метка Watchtower. `GIGACHAT_AUTH_KEY` — **только на машине, где гоняют
`tools/leaflet.mjs`**, в продакшене не нужен.

## Что ещё не решено

- **Название.** «Что у нас есть?» — предложение, не выбор. Растёт в инвентарь
  дома без переименования, но вопрос звучит шире, чем сервис умеет.
- **Магний в реестре веществ.** Его нет в списке свободных в
  `Design/services.md` — нужна строка в таблице. Если четыре фавикона рядом
  покажут, что барий всё-таки различим, решение можно откатить одной правкой
  переменных.
- **Общий каталог GTIN между домами.** Пока каждый дом ведёт свой, обмен
  только через `bank/`. Если домов станет больше трёх, вопрос вернётся —
  вместе с вопросом, кто чинит чужие опечатки.
- **OCR срока с упаковки.** Камера уже открыта, срок напечатан рядом с кодом;
  соблазн прочитать его автоматически большой, точность — низкая, а цена
  ошибки — просроченное лекарство, которое сервис считает годным. Не раньше,
  чем всё остальное будет работать, и только с обязательным подтверждением
  человеком.
- **Что делать с истёкшим.** Сейчас «выбросить» — событие в журнале. Пункты
  приёма просроченных лекарств есть не везде, и подсказывать их — отдельная
  задача с данными, которых у нас нет.
